# Transaction Ledger API — API Contracts

## 1. Overview

The Transaction Ledger API provides endpoints to manage accounts, perform credit and debit transactions, retrieve account balances and transaction history, and transfer money between accounts.

**Base URL:** `http://localhost:8080`

**Content-Type:** `application/json`

### Common conventions

- Account IDs and transaction IDs are generated by the application/database.
- New accounts start with a balance of `0.00`.
- Transaction types are `CREDIT` and `DEBIT`.
- Pagination is zero-based: the first page is `0`.
- Monetary values are represented as JSON numbers.
- Invalid requests return an error response according to the application's exception-handling configuration.

### Standard error response

The application uses the following general error response structure, based on the observed insufficient-funds response:

```json
{
  "timestamp": "2026-10-29T12:00:48.2969334",
  "status": 422,
  "error": "Unprocessable Entity",
  "message": "Insufficient funds. Available Balance: 0.00, requested amount: 120.00"
}
```

The timestamp and message vary depending on the error. The examples below illustrate expected error scenarios; confirm the actual status codes and messages against the running application.

## 2. Create Account

Creates a new account with an automatically generated ID and an initial balance of zero.

**Endpoint:** `POST /api/v1/accounts`

### Request body

```json
{
  "name": "Ruthik"
}
```

| Field | Type | Required | Validation |
|---|---|---|---|
| `name` | String | Yes | Must not be blank; maximum 100 characters |

The client must not provide fields such as `id`, `balance`, or `createdAt`. Unknown request properties are expected to be rejected when strict Jackson deserialization is enabled.

### Success response

**HTTP Status:** `201 Created`

```json
{
  "id": 7,
  "name": "Ruthik",
  "balance": 0,
  "createdAt": "2026-10-29T11:59:39.24623"
}
```

### Error responses

**HTTP Status: `400 Bad Request` — Missing or invalid name**

```json
{
    "timestamp": "2026-10-29T12:35:37.3937",
    "status": 400,
    "error": "Bad Request",
    "message": "Account name cannot be blank."
}
```

**HTTP Status: `400 Bad Request` — Unsupported field**

Example request:

```json
{
  "name": "Ruthik",
  "balance": 5000
}
```

Expected outcome: the request is rejected because `balance` is not an accepted field in the account creation request.

```json
{
    "timestamp": "2026-10-29T12:36:40.9830983",
    "status": 400,
    "error": "Bad Request",
    "message": "Invalid request body. Please check the supplied field values."
}
```

## 3. Get Account Details

Retrieves the details of an existing account.

**Endpoint:** `GET /api/v1/accounts/{id}`

### Path parameters

| Parameter | Type | Required | Description |
|---|---|---|---|
| `id` | Long | Yes | ID of the account |

### Success response

**HTTP Status:** `200 OK`

```json
{
  "id": 2,
  "name": "ruthik",
  "balance": 340.00,
  "createdAt": "2026-10-29T10:19:05.187713"
}
```

### Error response

**HTTP Status: `404 Not Found`**

Returned when the requested account does not exist, assuming the service maps missing accounts to a not-found exception.

```json
{
    "timestamp": "2026-10-29T12:37:30.0662134",
    "status": 404,
    "error": "Not Found",
    "message": "Account not found with ID: 999"
}
```

## 5. Create Transaction

Creates a credit or debit transaction for a specific account.

**Endpoint:** `POST /api/v1/accounts/{id}/transactions`

### Path parameters

| Parameter | Type | Required | Description |
|---|---|---|---|
| `id` | Long | Yes | ID of the account |

### Request body

```json
{
  "type": "CREDIT",
  "amount": 1000,
  "description": "Buying Chocolates",
  "referenceId": "PAY-0006"
}
```

| Field | Type | Required | Validation |
|---|---|---|---|
| `type` | String | Yes | Must be `CREDIT` or `DEBIT` |
| `amount` | Number | Yes | Must be greater than zero; maximum two decimal places |
| `description` | String | No | Maximum 255 characters |
| `referenceId` | String | Yes | Must not be blank; maximum 100 characters |

### Success response

**HTTP Status:** `201 Created`

```json
{
  "id": 1,
  "accountId": 7,
  "type": "CREDIT",
  "amount": 1000,
  "description": "Buying Chocolates",
  "referenceId": "PAY-0006",
  "balanceAfterTransaction": 1000.00
}
```

### Error responses

**HTTP Status: `400 Bad Request` — Invalid request**

Example: zero or negative amount, missing required fields, invalid transaction type, or amount with more than two decimal places.

```json
{
    "timestamp": "2026-10-29T12:38:25.2063847",
    "status": 400,
    "error": "Bad Request",
    "message": "Amount must be greater than zero"
}
```

**HTTP Status: `404 Not Found` — Account does not exist**

```json
{
    "timestamp": "2026-10-29T12:38:43.1339908",
    "status": 404,
    "error": "Not Found",
    "message": "Account not found with ID: 70"
}
```

**HTTP Status: `422 Unprocessable Entity` — Insufficient funds**

Example: attempting to debit `120.00` when the available balance is `0.00`.

```json
{
    "timestamp": "2026-10-29T12:39:07.1490375",
    "status": 422,
    "error": "Unprocessable Entity",
    "message": "Insufficient funds. Available Balance: 640.00, requested amount: 1000"
}
```

**Duplicate reference**

```json
{
    "timestamp": "2026-10-29T12:39:40.3253791",
    "status": 409,
    "error": "Conflict",
    "message": "Reference ID already exists: PAY-0006"
}
```

## 6. Get Transaction History

Retrieves paginated transaction history for an account, with optional filtering by transaction type.

**Endpoint:** `GET /api/v1/accounts/{id}/transactions`

### Path parameters

| Parameter | Type | Required | Description |
|---|---|---|---|
| `id` | Long | Yes | ID of the account |

### Query parameters

| Parameter | Type | Required | Default | Validation |
|---|---|---|---|---|
| `type` | String | No | No filter | `CREDIT` or `DEBIT` |
| `page` | Integer | No | `0` | Must be zero or greater |
| `pageSize` | Integer | No | `10` | Must be between 1 and 100 |

### Example requests

Get the first page with a page size of three:

`GET /api/v1/accounts/3/transactions?page=0&pageSize=3`

Filter by credit transactions:

`GET /api/v1/accounts/3/transactions?type=CREDIT`

Filter by debit transactions with pagination:

`GET /api/v1/accounts/3/transactions?type=DEBIT&page=0&pageSize=3`

### Success response

**HTTP Status:** `200 OK`

```json
{
  "accountId": 3,
  "transactions": [
    {
      "id": 12,
      "accountId": 3,
      "type": "DEBIT",
      "amount": 120.00,
      "description": "Transfer to Account B",
      "referenceId": "TRANSFER-1002",
      "balanceAfterTransaction": 250.00
    },
    {
      "id": 11,
      "accountId": 3,
      "type": "CREDIT",
      "amount": 30.00,
      "description": null,
      "referenceId": "TRANSFER-1001",
      "balanceAfterTransaction": 370.00
    }
  ],
  "pagination": {
    "page": 0,
    "pageSize": 3,
    "totalElements": 2,
    "totalPages": 1,
    "hasNext": false,
    "hasPrevious": false
  }
}
```

The example shows the response structure. The actual transactions and pagination values depend on the database contents.

### Error responses

**HTTP Status: `400 Bad Request` — Invalid pagination**

Example request:

`GET /api/v1/accounts/3/transactions?page=-1`

```json
{
  "timestamp": "2026-10-29T12:00:00",
  "status": 400,
  "error": "Bad Request",
  "message": "Page must be zero or greater"
}
```

**HTTP Status: `400 Bad Request` — Invalid pagination**

Example request:

`GET /api/v1/accounts/3/transactions?pageSize=-1`

```json
{
    "timestamp": "2026-10-29T12:41:05.5447024",
    "status": 400,
    "error": "Bad Request",
    "message": "Page size should be at least 1"
}
```

**HTTP Status: `400 Bad Request` — Invalid Transaction Type**

Example request:

`GET /api/v1/accounts/3/transactions?type=CRED`

```json
{
    "timestamp": "2026-10-29T12:41:36.4997366",
    "status": 400,
    "error": "Bad Request",
    "message": "Invalid transaction type. Allowed values are CREDIT and DEBIT."
}
```


**HTTP Status: `404 Not Found` — Account does not exist**

If the service checks account existence before returning transaction history, a missing account should produce a not-found response.

```json
{
    "timestamp": "2026-10-29T12:42:02.8171386",
    "status": 404,
    "error": "Not Found",
    "message": "Account not found with ID: 300"
}
```

## 7. Transfer Amount

Transfers money from one existing account to another.

**Endpoint:** `POST /api/v1/transfer`

### Request body

```json
{
  "fromAccountId": 7,
  "toAccountId": 6,
  "amount": 120,
  "referenceId": "TRANSFER-1003",
  "description": "Transfer to Account A"
}
```

| Field | Type | Required | Validation |
|---|---|---|---|
| `fromAccountId` | Long | Yes | Source account ID |
| `toAccountId` | Long | Yes | Destination account ID |
| `amount` | Number | Yes | Must be greater than zero; maximum two decimal places |
| `referenceId` | String | Yes | Must not be blank; maximum 100 characters |
| `description` | String | No | Maximum 255 characters |

### Success response

**HTTP Status:** `201 Created` *(confirm the status configured by your controller)*

```json
{
  "fromAccountId": 7,
  "toAccountId": 6,
  "amount": 120,
  "referenceId": "TRANSFER-1003",
  "status": "COMPLETED",
  "message": "Transfer completed successfully"
}
```

The response `referenceId` should match the request's `referenceId` when the service returns the submitted reference unchanged.

### Error responses

**HTTP Status: `400 Bad Request` — Invalid request**

Examples include a missing required field, an invalid amount, or a request with identical source and destination account IDs if this condition is mapped to `400`.

```json
{
  "timestamp": "2026-10-29T12:00:00",
  "status": 400,
  "error": "Bad Request",
  "message": "Source and destination accounts must be different."
}
```

**HTTP Status: `404 Not Found` — Source or destination account does not exist**

```json
{
  "timestamp": "2026-10-29T12:00:00",
  "status": 404,
  "error": "Not Found",
  "message": "Account not found With ID: 999"
}
```

**HTTP Status: `422 Unprocessable Entity` — Insufficient funds**

```json
{
  "timestamp": "2026-10-29T12:00:00",
  "status": 422,
  "error": "Unprocessable Entity",
  "message": "Insufficient funds. Available Balance: 50.00, requested amount: 120.00"
}
```

**Duplicate reference**

If the reference is already used for either account involved in the transfer, the request should be rejected according to the implemented duplicate-reference rules. Confirm the actual HTTP status and response body.

```json
{
    "timestamp": "2026-10-29T12:42:54.9214205",
    "status": 409,
    "error": "Conflict",
    "message": "Reference ID already exists: TRANSFER-1004"
}
```

A failed transfer should not leave only one account updated. Both account balance changes and both ledger entries should be committed or rolled back together.

## 8. General Error Scenarios

| Scenario | Expected HTTP status | Notes |
|---|---|---|
| Invalid request body | `400 Bad Request` | Bean validation or JSON deserialization failure |
| Invalid pagination | `400 Bad Request` | Negative page or page size outside the allowed range |
| Account not found | `404 Not Found` | Depends on service and exception-handler implementation |
| Insufficient funds | `422 Unprocessable Entity` | Observed application response |
| Duplicate reference | Verify implementation | Depends on the configured exception mapping |
| Unexpected server error | `500 Internal Server Error` | Unexpected failure not mapped to a more specific status |

## 9. Important Notes

1. Account and transaction IDs are generated by the application/database; clients should not supply them when creating records.
2. The transaction `referenceId` is supplied by the client and is distinct from the generated transaction ID.
3. Amounts must be positive and should not have more than two decimal places.
4. Transaction history supports optional type filtering and pagination.
5. Transfers create a debit entry for the source account and a credit entry for the destination account.
6. Transfer processing is intended to update both account balances and create both ledger entries atomically.
7. Exact error status codes and message text are determined by the application's validation and exception-handling implementation.
