# Transaction Ledger API — Assumptions

## 1. Account Management

1. Each account is assigned a unique ID generated automatically by the database.
2. A newly created account starts with a balance of `0.00`.
3. Account creation requires only the account holder's name.
4. Clients cannot set the initial balance or creation timestamp through the account creation request.
5. Account names must not be blank and cannot exceed 100 characters.
6. The account creation timestamp is generated by the application when the account is created.

## 2. Transaction Management

1. Every transaction belongs to an account.
2. Each transaction is assigned a unique transaction ID generated automatically by the database.
3. The supported transaction types are `CREDIT` and `DEBIT`.
4. Transaction amounts must be greater than zero and may contain a maximum of two decimal places.
5. A credit transaction increases the account balance by the specified amount.
6. A debit transaction decreases the account balance by the specified amount.
7. A debit transaction is rejected if the available balance is insufficient.
8. Each transaction records the account balance after that transaction is applied.
9. The transaction description is optional and cannot exceed 255 characters.
10. The `referenceId` is provided by the client and is separate from the automatically generated transaction ID.

## 3. Reference ID and Duplicate Prevention

1. A transaction reference ID must not be blank and cannot exceed 100 characters.
2. Duplicate transaction references are rejected according to the application's reference validation rules.
3. For regular account transactions, the duplicate check is performed using the account ID and reference ID.
4. During a transfer, the reference ID is checked against transactions associated with both the source and destination accounts.

The reference ID is therefore not the same as the database-generated transaction ID.

## 4. Transaction History and Pagination

1. Transaction history is retrieved for a specific account.
2. Transaction history can optionally be filtered by transaction type: `CREDIT` or `DEBIT`.
3. Pagination uses zero-based page numbering, meaning the first page is page `0`.
4. The default page number is `0`.
5. The default page size is `10`.
6. The minimum page size is `1`, and the maximum page size is `100`.
7. The history response includes pagination metadata such as total elements, total pages, and whether previous or next pages exist.

## 5. Money Transfers

1. A transfer moves money from one existing account to another.
2. The source and destination accounts must be different.
3. The transfer amount must be greater than zero and may contain a maximum of two decimal places.
4. The source account must have sufficient funds to complete the transfer.
5. A successful transfer creates two ledger entries:
   - A `DEBIT` transaction for the source account.
   - A `CREDIT` transaction for the destination account.
6. The source account balance decreases by the transfer amount, while the destination account balance increases by the same amount.
7. Both account balance updates and both ledger entries are intended to be committed together in a single database transaction.
8. If the transfer fails, the database transaction should roll back so that a partial transfer is not committed.
9. Account rows are locked in ascending account ID order to reduce the likelihood of deadlocks when concurrent transfers involve the same accounts.
10. The transfer response includes the source account ID, destination account ID, amount, reference ID, status, and message.
11. In the current implementation, the transfer description is recorded on the source account's debit entry. The destination account's credit entry is created with a `null` description.

## 6. Validation and Error Handling

1. Request payloads are validated before business operations are performed.
2. Invalid fields, missing required values, and invalid amounts are rejected.
3. Requests containing unsupported JSON properties are intended to be rejected when strict JSON deserialization is enabled.
4. Requests for accounts that do not exist should be rejected by the relevant service operation.
5. Insufficient-funds errors use HTTP `422 Unprocessable Entity` in the observed implementation.
6. Other error status codes and response messages follow the application's configured exception handling.

## 7. Database and Configuration

1. MySQL is used as the application's persistent database.
2. Flyway manages database schema migrations.
3. Migration scripts are maintained under `src/main/resources/db/migration/`.
4. Database connection details are configured in `src/main/resources/application.yml`.
5. Developers must configure their own local MySQL credentials before running the application.
6. Database passwords and other sensitive credentials should not be committed to version control.

## 8. Scope and Limitations

1. The application implements account management, credit and debit transactions, transaction history, and account-to-account transfers.
2. Authentication, authorization, and user-specific access control are outside the current scope unless separately implemented.
3. The reference ID checks provide duplicate prevention within the implemented validation rules; they should not be assumed to provide globally unique transfer idempotency.
4. The API is intended to maintain consistent account balances and ledger entries through transactional database operations.
